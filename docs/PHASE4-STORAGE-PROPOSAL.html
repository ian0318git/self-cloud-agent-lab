哪些狀態要活過重啟

item 4、5、6 不是三件事。它們是同一個問題的三個面孔：哪些狀態必須活過一次重啟，而它們要放在哪。 D-030 判定 item 5（第二套向量庫的維運成本）「前提不成立」——沒有東西可以備份、遷移或保持一致。那個前提之所以不成立， 正是因為狀態活不過行程結束。這一頁問的是：要不要讓它成立。

一句話要先分清楚：探針用暫存目錄是對的。 每次量測都必須從乾淨的狀態開始，否則量到的數字會取決於上一次的殘留——:289 每次用新的 thread_id 就是為了這個。不要為了「落地」去改探針的預設； 要回答的是第四階段的服務：它的狀態放哪。

貳選項：放在哪

機制其實已經有了：探針有 --workdir，只是進入點從來沒傳過它、容器也沒掛任何 volume。 所以這不是「要不要寫功能」，是「要不要把線接起來、接到哪」。

A · 新增一個具名 volume

建議
是什麼
第三個具名 volume，掛進第四階段的服務容器。
好處
與既有慣例一致（compose 現有兩個都是具名 volume）；deploy-vps.sh 在失敗路徑上 保證「down 不帶 -v，volume 完好」；備份是一行 docker run --rm 打包。
代價
看不到。要 docker volume inspect 或進容器才摸得到內容。

B · bind mount 進專案目錄

是什麼
例如 ./data/mem0，直接掛主機目錄。
好處
看得到、好備份、好檢查，不必學新指令。
代價
把執行期資料放進工作樹（要 gitignore，VPS 上擁有者與權限要對）；專案原本刻意沒有這個慣例， 而且它落在 down -v 的保證之外。

C · 維持現狀

是什麼
不落地，每次重啟歸零。
好處
零改動，也沒有新的維運面。
代價
第四階段的「記憶」等於沒有——等於把 D-036 花四小時買到的抽取能力， 放進一個每次清空的容器裡。

順便決定的：一致性單位

三個消費者要共用一個 volume（/state/mem0、/state/jobs.sqlite、 /state/checkpoints.sqlite），還是各自獨立？

  • 共用——備份是一個時間點的一致快照。「還原了 checkpointer 卻指向別的日期的記憶」 這種不一致，結構上不可能發生；搬遷文件也只多一行。D-030 的判準本來就是「有沒有東西可以不一致」。
  • 各自獨立——爆炸半徑小，一個壞掉不拖累其他。但「一致」變成要自己維護的性質。

另一件要在這裡講清楚的事：deploy-vps.sh 只支援全新安裝、不搬資料 （它刻意不用「volume 存不存在」當判準——模型與 volume 是可重建的產物，帳號與對話不是）。 記憶屬於「不是」那一邊，而目前沒有任何程序會搬它。所以這件事要在這裡決定， 不會有別的時刻替你決定。

向量庫不是磁碟問題。7 MB 對上 17.12 GB 的可回收映像，差了三個數量級。 D-030 的三段判定（ok／reclaim-first／blocked）在這一台是 reclaim-first——不是放不下，而是先清再放。 順序因此是：先 reclaim，再決定落地的位置。 理由不是向量庫大，是 / 已經 82%，而第四階段還會拉新映像與更大的模型。

肆子決定：misfire_grace_time

這一項量得很乾淨，而且量出來的結論比參數本身重要。

  • APScheduler 的預設寬限是 1 秒。
  • 邊界是「逾期 > 寬限 ⇒ 丟掉」，而且邊界隨 grace 移動：固定逾期 2.2 秒時，grace 1 丟掉、grace 3 跑掉。
  • 最關鍵的一條：丟掉與跑過在 store 裡長得一模一樣。 沒有外部紀錄就分不出來——這才是這一項的發現。
選項
值 重啟之後的行為 適合
吃預設 1 秒 停機超過 1 秒的 job 靜默消失 一律準時才有意義的 job
一個明確的窗口例：300 秒 涵蓋一次重啟的停機，但不重播一週前的排程 大部分維運型 job
None ＋ coalesce=True 一律補跑，且不會補跑風暴 少一天就是少一天的 job（每日摘要）

不管選哪一個，都必須有外部紀錄（fire 與 drop 都要留痕）， 否則這個值只是在選一種沉默。值本身是次要的，可觀測性才是主要的。

另外兩條量到的限制會反過來約束第四階段的程式碼怎麼寫，所以要在寫 job 之前決定： run_date 必須是 datetime（float timestamp 直接 TypeError）； 而 SQLAlchemyJobStore 拒絕非模組層級的 job——lambda 當場失敗，記憶體 store 卻收得下。

伍與 item 4 的耦合

item 4（每個 graph 自己的 recursion_limit）沒辦法單獨做，因為它要讀的數字就是存在 checkpointer 裡的：

  • 讀「這張 graph 走到第幾步」要靠 get_state(cfg).metadata["step"]，而那需要 checkpointer ＋ thread_id。
  • D-030 的對照組已經量完：中斷之後有 checkpointer 只是多花一次呼叫，沒有就是全部重跑。

所以：要收緊 recursion_limit，checkpointer 就是前置條件， 而 checkpointer 放在哪就是這一頁的問題。item 4 與 item 5／6 是同一個決定的兩半。

陸建議

  1. 走 A，而且三個消費者共用一個 volume。新增一個具名 volume， 三個消費者是它底下的三個子路徑。與既有慣例一致、備份即一致快照、搬遷文件只多一行。
  2. 探針不動。暫存目錄是量測正確性的一部分。落地是第四階段服務的事， 機制用既有的 --workdir 或服務自己的設定。
  3. misfire_grace_time 明講一個值，並在同一個改動裡 加上 fire／drop 的外部紀錄。沒有紀錄就不算決定。
  4. 順序：先 reclaim 17.12 GB，再建 volume。不是因為向量庫大，是因為 / 已經 82%。

柒要你決定的四點

  1. 落地走 A（具名 volume）、B（bind mount）還是 C（維持現狀）？
  2. 三個消費者共用一個 volume，還是各自獨立？
  3. misfire_grace_time 取哪個值（預設 1 秒／明確窗口／None ＋ coalesce）？ 以及外部紀錄放哪（log 檔？同一顆 sqlite 的第三張表？）
  4. 要不要把第四階段服務的狀態路徑寫進 .env.example？今天那 13 個旋鈕裡沒有任何記憶或排程路徑。
